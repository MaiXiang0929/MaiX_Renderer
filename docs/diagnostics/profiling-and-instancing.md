## 不透明实例绘制

Instancing（实例绘制）让多个同网格同材质对象共用一次绘制调用。`RenderScene` 先排序，批次要求着色器、材质与网格编号全部相同；单项批次走普通绘制，多项标准三角形批次走实例路径。透明和 Tessellation（曲面细分）保持逐项提交。

CPU（中央处理器）每个实例计算一张 64 字节观察矩阵 `V×M`，写入 UBO（统一变量缓冲对象）。GPU（图形处理器）用 `gl_InstanceID`（实例下标）读取矩阵：

```text
观察空间位置 = 实例观察矩阵 × 局部位置
裁剪位置 = projectionFromView × 观察空间位置
灯光位置 = lightFromView × 观察空间位置
法线 = 实例观察矩阵逆转置 × 局部法线
```

`projectionFromView=VP×inverse(V)`，`lightFromView=lightVP×inverse(V)`，避免每实例同时上传多个矩阵。法线矩阵在顶点着色器计算，保留非均匀缩放正确性，但仍有每顶点逆矩阵运算成本。

OpenGL 4.0 的可移植统一块下限 16 KiB（16 千二进制字节）容纳 256 张矩阵，因此一个大批次按 256 实例切块。Forward 与 Shadow 各自拥有实例缓冲，反射复用 Forward 的缓冲；阴影缓冲上传的是灯光变换矩阵并过滤不投影项。

缓冲按驱动的统一缓冲偏移对齐，容量按需增长，采用六个循环区域和一次区域上传。区域轮转降低立即覆盖旧数据的概率，但没有 Fence（同步栅栏）证明 GPU 已消费；仍依赖 OpenGL 更新语义和驱动同步，不能称作保证无阻塞的显式同步系统。前向上传准备失败时回退逐项绘制。

## 顶点数组状态缓存

VAO（顶点数组对象）绑定缓存只跟踪当前顶点数组，相同对象连续提交时跳过实际绑定。每个渲染阶段开始失效；网格上传、删除及部分直接绑定路径也失效，避免不经缓存的操作改变真实状态。

历史透明场景三次绘制共享同一网格，统计为请求 3 次、变化 1 次，因此只保留必要的首次绑定。当前不缓存 Program（着色程序）或 Texture（纹理）；请求/变化计数可以发现潜在冗余，但计数本身不阻止调用。

## 统计口径

| 数据 | 表示什么 | 不能据此推断什么 |
| --- | --- | --- |
| 视图源对象、可见对象、裁剪对象 | 主视图提交准备情况 | 总场景三角形开销 |
| 不透明绘制项与批次 | 排序后列表规模 | 实际绘制调用数 |
| 每阶段绘制、实例数 | 已接入提交入口的调用与实例数量 | 驱动全部内部命令 |
| 着色器/材质/网格/纹理请求与变化 | CPU 提交及相邻身份变化 | CPU 毫秒耗时或 GPU 带宽 |
| GPU 阶段时间 | 查询覆盖的阶段执行时间 | 整个编辑器帧时间或呈现等待时间 |

CPU 侧目前主要是提交次数统计，没有独立逐阶段 CPU 毫秒计时器。反射内透明绘制计入反射阶段，不计入主透明阶段。日志仅在提交统计变化时输出；界面读取快照，无需接触阶段内部容器。

## 非阻塞 GPU 时间查询

Timer Query（时间查询）使用 `GL_TIME_ELAPSED`（经过时间查询）包围每个阶段。三组帧槽循环使用，复用前先检查所有查询结果可用；尚未就绪时跳过该帧采样，不覆盖查询，也不主动等待 GPU。

时间从纳秒换算为毫秒，保存最近完成值与 EMA（指数移动平均）：新平均值按 0.1 权重加入新样本。它有帧延迟，初始样本无效时界面显示空值。阶段时间之和不包括全部界面渲染、窗口交换或 GPU 等待。

查询创建失败只关闭计时，渲染初始化可以继续。异常终止的管线帧可能没有完整阶段查询，因此诊断完整帧时应先排除资源契约错误。

## 图形捕获

GpuDebugScope（GPU 调试范围）尝试使用驱动支持的调试组函数，缺失时退化为空操作，不提高最低 OpenGL 版本。当前十阶段标记对应管线顺序，RenderDoc（图形帧捕获分析工具）可以按标记检查纹理、深度、混合与绘制数量。

建议固定构建类型、视口大小、场景与相机，记录开关，等待资源重建结束后捕获。性能比较需要多帧样本与相同环境；历史单次最终平均值只能作为方向性记录，不能推断统计显著加速。

运行 `--instance-grid 16` 生成 256 个共享资源对象，观察主视图项数与真实阶段绘制数的区别。历史数据及捕获文件说明见[性能基准](benchmarks.md)。
